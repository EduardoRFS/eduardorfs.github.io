Induction and self dependent types

When moving from Lambda Calculus to a dependently typed version of the Lambda Calculus such as the Calculus of Constructions one may want to do proofs by induction, but this is not a trivial matter.

Church Encoding

Compute power can be internalized using strictly lambdas using Church encoding as shown by Internalizing computing, so let’s try to apply the same technique here.

This given type for Bool has 3 distinct problems.

Type recursion, (P : Bool -> Type) -> _, here is “okay”, as Bool appears strictly in a positive and erasable position, allowing a traditional fixpoint to works.

Mutual recursion, P true -> P false -> P _, is weird but could likely in principle be accepted as long as it only appears in positive and erasable positions which is the case here.

Self dependency, the P b, requires something novel, somehow the type of the boolean would need to depend on the instance of the boolean, during the type definition itself.

GADT’s

Self Dependent Types

When looking at specific instances of ind_bool, some of the desirable behaviour can be seen. As what is known as “very dependent types” aka when the type of a term depend on itself. So I will be calling those: Self Dependent Types.

Self Types

The example above shows that mutual recursion is almost enough(in fact it may be enough) and that likely the only missing requirement is a way of abstracting over self. Peng Fu and Aaron Stump originally proposed a way to solve this issue, as part of Self Types, a type where the type itself can depend on it’s own instances.

This when combined with mutual recursion would allow for induction through lambda-encodings.

While self types works, it comes with many issues, first, the typing rule for self is weird. Somehow before @self(x). T is checked to be a type it is already added in the context, this makes it an assumption, while it works from a logics point of view, it makes designing an algorithm more annoying and making it rely on assumptions.

Additionally in this convenient way it would rely on Bool to expand inside of itself, leading to also another assumption on the fixpoint, this is not required but using self types without the fixpoint magic is hard.

There are a couple tricks that can be done to improve it here, integrating it on the fixpoint is one option, which subsumes mutual recursion as self-types allows for induction-induction.

Self + Fix

While the first presentation leads to a very small calculus, it does one weird substitution during type checking on the fixpoint, which makes me feel uneasy, additionally it is not ergonomic.

Delayed Self

Another interesting presentation is to delay the assumption, by placing them on the introduction and elimination rule, this allows to easily retrofit self-types in existing systems. This seems to be weaker as I was not able to encode induction-induction using simple recursion, but if mutual recursion is allowed it works naturally.

This works and in fact can be made quite ergonomic, but it is weird, as in it seems like there is a more general solution to it, what if the equality constraint is lifted?

Dependent Intersection

An alternative to self-types proposed also by Aaron Stump are Dependent Intersections, which while they don’t require mutual recursion, they require a curry-style presentation.

Church Encoding

One of the most natural things to do in the Lambda Calculus is to describe data such as the booleans, naturals, pairs and list. This is often done through Church encoding, but most people don’t seem to be able to mechanically derive those encodings.

Computing Power

The main insight provided here is that church encodings is just the internalization of the elimination function for some data.

Every data structure seems to come with a function that is capable of doing every fundamental operation on the data itself. This single function provides all the computing power possible for the data. Such as case for booleans and fold for list.

In fact, it is easy to notice that anything that can describe case can be used as a boolean, such as using the empty list as false and all non-empty list as true.
